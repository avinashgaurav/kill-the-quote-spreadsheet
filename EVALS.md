# Reading accuracy evals: first recorded Claude runs

Three runs on 2026-10-15 against the fictional corpus: a baseline full run, a documents-only repeat, and a full rerun after two fixes. These are early measurements on Claude, not a benchmark.

## Method note

Measured via the Claude Code CLI with the app's own system prompt and JSON schema, not the production API path; an API rerun is planned.

Concretely: `LLM_PROVIDER=claude-cli` (opt-in only, in `web/lib/llm.ts`) sends each call to `claude -p` with:

- the extraction system prompt from `lib/extract/run.ts` via `--system-prompt` (replaces Claude Code's own)
- the same content blocks the Anthropic path builds (line catalog text, reader guidance, the document as text, a base64 image block or a base64 PDF document block), sent as a stream-json user message
- the forced `report_extraction` tool's `input_schema` passed as `--json-schema`. The structured output comes back as that tool's arguments and is then parsed with the same Zod schema and `validateExtraction()` as production.
- no tools, no MCP, no hooks, CLAUDE.md, skills or plugins (`--safe-mode`), no settings files, no session persistence, `--effort high` (as production)

## What is measured

`npm run accuracy` (`web/scripts/accuracy.ts`) runs the real extractor (`extractDocument`) on each document and scores the read against the answer key the generators wrote the documents from. The harness switches the crop re-read off, so the reader is scored on its own.

| Metric | Definition |
|---|---|
| Recall ("found") | Of the lines the supplier priced, how many came back with a price |
| Price | Of those, how many match the key to the rupee |
| Unit | How many carry the unit the supplier wrote (pack size must match) |
| Invented ("made up") | Prices returned for lines the supplier never priced. Target is zero |
| Illegible admitted | Values the key marks unreadable that came back without a number |
| Calibration | Whether confidence falls when accuracy falls, per photograph |

The harness fails a run on any of these: an invented price, recall below 85%, price exactness below 90%, a document that did not read, a guess at an unreadable value, or wrong prices at mean confidence above 0.75.

One scoring change came with the fix: a line the key prices at 0 is now scored from the reader's raw row. Before, it was scored from the validated row, where `validateExtraction` deliberately nulls every zero so that it can never win a line. A zero in any unit is zero, so its unit is not scored. This does not rescore the baseline: there the reader returned a null price for that line, which is a miss either way.

## Dataset

Fully fictional, generated by `dataset/generators/` (no real company, supplier or price). Answer key: `web/lib/data/raw-quotes.json`.

- 5 vendor replies, one per format: Zenith xlsx, Cygnus pdf, Orbit docx, Vector jpg photo, Helios eml. 107 priced lines in total (30, 27, 27, 21, 2).
- 5 photographs of the same 22-line rate card, from easy to very hard (flat, handheld, curl and thumb, low light, steep angle). Each has 21 priced lines plus 1 value the key marks unreadable (glare).

## What changed before the rerun

Both fixes ship in the same PR as these eval results:

1. **An empty citation no longer fails the whole read.** In the baseline, one Vector photo row came back with `citedText: ""`. Zod's `min(1)` threw, and a read with 21 prices was reported as failed. Now:
   - the row is kept and flagged by `validateExtraction`, with confidence capped at 0.4 (the same treatment as a price with no unit);
   - the calculator gets a new `unsourced` flag, derived from the stored provenance, and keeps the value out of every total, the same treatment as a contested photo read;
   - the tool description asks for non-empty text.

   `minLength` was deliberately **not** added to the schema. Anthropic's strict tool schemas do not support string-length constraints, and `llm.ts` sends this schema raw, so adding it could break the production path rather than enforce anything.
2. **Lines that are included or free are priced at 0.** In the baseline, Orbit L30 ("included in our laptop prices at no additional charge") was found and cited correctly, but came back as `bundled` with a null price. Validation turns that combination into `illegible`, which tells a buyer to open the original for a sentence that was read perfectly. The system prompt and the price field now say such a line is price 0, status `quoted`. The normaliser already routes a 0 to review and never ranks it (regression case 8).

New offline regression cases 48 and 49 cover both fixes. `npm run test:all` stays green.

Calibration held in both runs. On v4 every wrong price carried confidence of 0.60 or less in the baseline, and 0.55 or less after the fix: below the 0.8 floor at which the UI flags a value as low-confidence. Mean confidence on wrong prices was 0.50, then 0.47. The unreadable glare value was admitted on every photograph in both runs, and no photograph was flagged as confidently wrong. Accuracy spread was 71 points, then 67; confidence spread was 40, then 46. Neither fix targeted the photographs, so the v4 movement is run-to-run variation.

**Headline:** after two fixes derived from this same corpus, 107 of 107 priced lines came back exact on price and unit, nothing was invented, and the harness passes. The low-light photograph is still mostly misread (33%), but at low confidence.

## Not run

- The analyst tool-call questions. `accuracy.ts` has no analyst mode, and the analyst is a multi-turn loop with ten custom tools, which this CLI route does not support (it throws rather than approximate it).
- Questionnaire and certificate reads (calls 4 and 5 in `AI-MAP.md`), which are outside this harness.

## Differences from the production path

- The CLI prepends a one-line preamble and an environment block (working directory, platform, date) to the system prompt, and adds a short account-context note to the user turn.
- Structured output is enforced by the CLI's StructuredOutput tool plus `--json-schema`, not by `tool_choice` with `strict: true`. If the model answers in text first, the CLI asks it again to call the tool.
- `max_tokens` (16,000 in production) and the prompt-cache breakpoint after the line catalog cannot be set; the CLI uses its own.
- PDF citations are not surfaced, so `supportsCitations()` stays false and the Cygnus PDF read is flagged `provenanceWeaker`, as on Gemini. Scoring does not use citations.
- Usage: `input` includes cache writes on this route, and cost is the CLI's figure, not the app's.
- The extraction cache key includes the model id, which is the same as on the Anthropic route, so every run used `--fresh` and wrote nothing to `.cache/`.
- Unverified, worth checking on the API rerun: the Anthropic docs list structured outputs as incompatible with citations (a 400 error). Production sends PDFs with `citations: {enabled: true}` alongside a `strict: true` forced tool. This route cannot test that combination.

## Reproduce

```bash
cd web
npm ci
npm run test:all                                   # offline suites, no key
LLM_PROVIDER=claude-cli npx tsx scripts/accuracy.ts --all --fresh \
  --json ../evals/results/accuracy-<date>-claude-cli-claude-opus-5.json
# documents only: drop --all. Model: CLAUDE_CLI_MODEL=<id>
```

Each CLI call is killed after 300 s (`CLAUDE_CLI_TIMEOUT_MS` to change it; the slowest read in run 1 took 334 s). The route refuses to run under `NODE_ENV=production` unless `ALLOW_CLAUDE_CLI_EVAL=1`.

`--json <path>` is optional; without it the harness prints only. The production-path equivalent (planned) is the same command with `ANTHROPIC_API_KEY` set and `LLM_PROVIDER` unset.

## Held-out run

The 107/107 above is an in-sample score: the reader prompt and both fixes came from that same corpus. This run measures the reader on documents it has never seen.

**Method.** Five new fictional vendor replies against the same RFx (the buyer's enquiry is an input, not an answer), built by `dataset/generators/build_heldout.py` into `dataset/heldout/`. The suppliers, prices, layouts and line selection are all new:

- Kestrel xlsx: two sheets, the supplier's own item codes, a GST column, a regret, a substitution and a per-piece line.
- Tarang pdf: two pages with rate and amount columns side by side, one USD line, a per-cartridge line and a regret.
- Nilgiri docx: a letter with Indian digit grouping in prose, a per-pair line and a complimentary (zero) line.
- Tejas: one quotation sheet photographed twice (moderate, and very hard: low light, motion blur, slight curl), with two pen overrides and one price under glare.
- Saptarishi eml: plain text, with a per-box-of-25 line, a relative price and a regret.

That makes 77 priced lines over 6 inputs, plus 1 value the key marks unreadable on each photograph. The answer key (`dataset/heldout/answer-key.json`) was committed in `53a6e8d`, before any model read the set. The prompts and `web/lib` were not changed. `accuracy.ts --heldout` scores the set with the same scoring and the same fail checks. Three full runs, `--fresh` each time.

The method note above applies unchanged: these runs used the Claude Code CLI path (`LLM_PROVIDER=claude-cli`, `claude-opus-5`, `CLAUDE_CLI_TIMEOUT_MS=400000`), not the production API.

| Metric | In-sample (run 3 above) | Held-out, mean (min to max, 3 runs) |
|---|---|---|
| Priced lines exact on price | 107/107 documents (100%) | 71.3/77 (92.6%), 70 to 72 |
| Lines returned | 107/107 | 76.7/77, 76 to 77 |
| Unit right (of returned) | 100% | 75.7, 75 to 76 (one harness artefact each run, see below) |
| Invented prices | 0 | 0, 0 to 0 |
| Unreadable value admitted | 5/5 photographs | 2/2 photographs, every run |
| Mean confidence on wrong prices | 0.47 (photo set) | 0.65, 0.61 to 0.69 |
| Highest confidence on any wrong price | 0.55 | 0.70 |
| Harness verdict | pass | pass, 3 of 3 |

Per input, every run: Kestrel 18/18, Tarang 13/13, Nilgiri 11/11, Tejas moderate photo 15/15 and Saptarishi 5/5, all exact. Every miss was on the very hard Tejas photograph, which read 10, 8 and 10 of 15. Without that photograph the held-out set is 62/62 in all three runs.

Two caveats. First, the two corpora are not the same size or mix, so the 92.6% against 100% is not a like-for-like drop. The in-sample 107 counts documents only (its photo set is scored separately), while the held-out 77 includes the very hard photograph. Second, the wrong prices sat at higher confidence than in-sample (0.65 against 0.47 on average, up to 0.70). Every one is still below the 0.8 line at which the UI flags a value as low-confidence, and the harness's 0.75 calibration check passed in every run, but the margin is smaller.

| 9 | Kestrel xlsx | L13 | 1, 2, 3 | Unit returned as "Kit (2x16GB)" against a key of "kit" | Harness artefact, not a reader error |

The Kestrel unit miss is the scorer, not the reader. The sheet's unit cell really says "Kit (2x16GB)". The unit matcher treats the "2" as an invented pack size because the key records the unit as "kit". The scoring code was frozen for this task, so the miss is left in the numbers.

The same matcher strips "nos", "pc" and "each", so the unit check means nothing on lines keyed that way. It only bites on pack, box, kit, cartridge and pair units. This was true of the in-sample corpus as well.

The pen overrides (Tejas L9 and L29) were read as the handwritten price in every run on both photographs. The relative price and the three regrets (Saptarishi L21, L23; Kestrel L14; Tarang L16) never came back as a number. The complimentary line (Nilgiri L30) came back as 0, and the per-cartridge, per-pair and per-box-of-25 lines came back in the supplier's unit (the per-piece line passes the unit check whatever comes back, see above).
